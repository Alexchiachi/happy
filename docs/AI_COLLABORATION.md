# AI 協作分工：戰略層與戰術層

**日期**：2026-08-29
**適用**：簡家旗的網站與內容發佈
**一句話**：AI 負責戰略層與戰術層的發佈，微信自成一套，不勉強統一。

---

## 網站分層

| | 戰略層 | 戰術層 | 微信公眾號 |
| --- | --- | --- | --- |
| 是什麼 | 簡家旗個人 IP，經營三年 | 雲南台灣選物、資訊交流 | 大陸通路 |
| 位置 | daoissimple.com | GitHub Pages（本 repo） | 微信 |
| 技術 | WordPress + Blocksy，cPanel 共享主機 | 靜態站，push 到 `main` 即上線 | 微信自有 |
| 變動節奏 | 慢，每次份量重 | 快，要迭代 | 獨立 |
| 出錯成本 | 高——三年累積的信任 | 低——改回來就好 | — |
| 該優化什麼 | **穩定、長壽** | **速度** | — |
| 收費實操 | **在這裡**（見 `wordpress/inner-flow/`） | 不在這裡 | 不在這裡 |

未來會有更多戰術級網頁出現在 GitHub。需要實操收費的一律回到戰略層。

**這個工具配對是對的，不是巧合。** 戰術層要試、要換、要快，git + 靜態站在這裡優勢壓倒性。
戰略層不該追求迭代速度——三年的個人 IP，價值在累積的一致性，不在改得快；那裡
「AI 接不上」的代價本來就低，改起來稍微麻煩反而有剎車作用。

## 分工

**AI 負責**

- **戰術層的發佈**：寫文章、建新頁面、維護既有七頁。內容在 git 裡，
  改動看得見（`git diff`）、退得回（`git revert`）、push 到 `main` 就上線
- **戰略層的文案**：在對話裡寫稿與改稿，由人貼進 WordPress 後台。
  不接自動化，理由見下
- **未來的戰術站**：同一套作法

**AI 不負責**

- **微信公眾號**。微信做微信的，不勉強統一。
  （限制記錄：2025 年 7 月起個人主體／未認證帳號的發布接口權限被回收；
  草稿箱 API 仍可用，但最後按發布是人工的。外鏈也受限——這是通路設計問題，
  不是技術問題。）
- **WordPress 的主題、外掛、設定**。那些在後台手動做

## 決策一：戰略層不接自動化

**結論：不接。** 用後台編輯 + 對話寫稿，加上一個文章範本。

評估過三條路：自己寫的 REST API 工具、官方 MCP Adapter 外掛、
Jetpack + WordPress.com 連接器。全部不採用，理由相同。

### 為什麼：瓶頸是照片，不是文字

表面上的算法：每篇省下「貼進後台 + 排成區塊」約 10 分鐘，
以目標值每月 6 篇算，一年約 12 小時。看起來划得來。

**但這個算法錯了。** 這個站的設計系統是照片主導的（`docs/DAOISSIMPLE_SITE.md`：
「雲南建議山霧、茶倉、職人雙手」）。每一篇都要進後台上傳照片、挑圖、設首圖——
任何 AI 整合都幫不上，圖片走媒體庫，是手工活。

**人本來就會待在後台。** 人在那裡了，順手貼一段文字的邊際成本接近零——
實際約每篇 3 分鐘。

重算：6 篇 × 3 分鐘 = 每月 15 分鐘，**一年約 3 小時**。

而且**每月 6 篇是目標，不是現況**——實際產出遠低於此。用目標值算都不划算，
用現況算差距更大。

為了一年 3 小時養一條要付月費、要維護、會壞掉的整合鏈，不划算。
**自動化省下的是一趟本來就要走的路。**

### 改成做這兩件事

**一、做一個文章範本**

在後台寫一篇草稿把骨架排好（開場摘要 → 內文 → 引言區塊 → 圖說 → 分隔），
標題寫「_範本 · 不要發布」。之後每篇複製它來改，排版時間歸零。
思路同靜態站的 `journal/_template.html`。

**二、寫稿時貼上品牌守則**

真正省時間的是讓 AI 第一次就給對調性，不用來回改三輪：

```
我在維護「大道至簡 daoissimple.com」的網站文案。改稿請遵守:

語氣
- 繁體中文,用字克制。不用驚嘆號堆疊,不用「超值」「限時」「錯過可惜」
- 說具體的事:地點、節氣、人的手做了什麼。不要說抽象的好
- 產地故事優先於功效宣稱。不要寫療效(天麻相關尤其注意,有法規風險)

品牌禁區(這些是刻意的,不要「順手優化」掉)
- 不要加 banner 輪播、彈窗、閃爍特價
- 留白很多是對的,不要為了多塞東西壓縮
- 雲南(茶褐)與台灣(苔綠)是對稱並列的雙翼,
  不要讓一邊變成主、一邊變成附屬
- 慢,是這個品牌的主張

文章分類只有四種:生活提案／產地故事／選物筆記／二地對話

改完只給我改後的文字,不要解釋,我要直接貼回 WordPress。
```

規矩取自 `docs/DAOISSIMPLE_SITE.md` 的〈設計取捨筆記〉。**那份筆記改了，這段要跟著改。**

## 決策二：暫不把文章來源改成 Markdown

曾提議把 `journal/` 的文章從手寫 HTML 改成 Markdown + 產生器。**目前撤回。**

當初的理由有一半是「微信也能從 Markdown 生成」。微信既然自成一套，
這個理由消失了。剩下的理由（未來的戰術站可共用、寫作時不用跟標籤打架）
在只有兩篇文章、第二個戰術站還沒出現的現在，不足以支撐這個改動。

**重評時機**：第二個戰術站真的要開，或 `journal/` 的文章累積到十篇以上。
兩者任一發生就該做——越晚越貴，因為要轉的文章越多。

## 還沒解決的事：備份

**這跟 AI 無關，但它還在，而且比自動化重要。**

daoissimple.com 沒有 staging、備份狀態不明。

- **免費解**：UpdraftPlus，資料庫每日、檔案每週，遠端存到 Google Drive。
  設定完**一定要去 Google Drive 用眼睛確認檔案真的在**——網站上顯示「成功」
  只代表打包完成，傳輸那段仍可能失敗
- **付費解**：Jetpack 的 VaultPress Backup，即時備份、一鍵還原

**不要因為想接 AI 才去買 Jetpack。要買就因為它是備份。**

## 什麼時候該重新評估

出現下列任一狀況，決策一就該重算：

1. **戰略層發文量顯著上升**，或出現不需要配圖的內容型態——
   照片是關鍵論證，這個前提一變，結論就變
2. **要做批次改動**——全站文案改版、統一調整 SEO 標題描述。
   那是一次性的大量重複工作，自動化在那種場合才真正划算
3. **官方方案變成免費或內建**——目前 Jetpack MCP 需付費方案
4. **有第二個人要發文**——那時後台的價值會遠高於任何指令列工具

重算時問同一個問題：**扣掉本來就要在後台做的事，實際還省下多少？**
